Where does your GPU's time go?

Every moment a deep learning program runs, the GPU is doing one of three things. Learn to spot which one is slowing you down, and you'll know what to fix.

A hands-on companion to Horace He's essay Making Deep Learning Go Brrrr From First Principles.

Speeding up the wrong thing does nothing

People often speed up deep learning code with a grab bag of tips from the internet. The essay's point is simpler: first find out which of the three kinds of time dominates. That alone tells you which fixes are a waste of effort.

If the factory is waiting on trucks, a bigger factory won't help. If the factory is already flat out, faster trucks won't help. Try it.

This gets harder every year. Chip makers keep making the math faster much more quickly than they make memory faster, so the factory keeps growing faster than the trucks can keep up.

2

Compute: the factory

A FLOP is one floating-point operation: a single add or multiply on decimal numbers. FLOPS is how many of those a chip does per second. An NVIDIA A100 GPU is advertised at 312 trillion per second, or 312 teraflops.

Ideally you want to be compute-bound: spending your time on math, the thing you paid for. Math is also the one cost you can't remove without changing what your model calculates. Memory traffic and overhead can be cut.

There's a catch. Most of that speed comes from Tensor Cores, circuits built only for matrix multiplication (matmul): multiplying big grids of numbers, the core of every neural network.

Normalization and pointwise operations (operations that change each number on its own, like an activation function) do almost no math but take 39% of the time. They get 250 to 700 times less work done per second than matmuls. The factory isn't the problem. The trucks are.

3

Memory: the warehouse and the trucks

The factory has a tiny, very fast storeroom, called SRAM. Everything else lives in a big, slower warehouse, called DRAM or global memory. DRAM is the memory nvidia-smi shows, and the one that runs out when you see "CUDA out of memory".

The rate at which data can move between them is the memory bandwidth. Every GPU kernel, the function the GPU runs for one operation, ships its input in from the warehouse and its result back out.

For something like x.cos(), the GPU does one tiny calculation per number but has to move every number twice. Nearly all the time goes to shipping. That's a memory-bound operation.

The fix is operator fusion: do several operations in one trip, keeping the data in the factory between them. The essay calls it the most important optimization in deep learning compilers.

Things to notice

Adding more operations to a fused chain barely changes its time. That's why a complex activation like GELU costs about the same as a simple one like ReLU: the math is nearly free, and the trip is the cost.

This also explains rematerialization, or activation checkpointing. Recomputing a value can be cheaper than storing it and reading it back later, so you can save memory and time at once.

Fusion isn't free. PyTorch's default eager mode runs each operation as soon as Python reaches it, so it can't know what comes next. A compiler (NVFuser and XLA are the essay's examples) has to see the whole chain and generate GPU code for it. To write fused kernels yourself, the essay suggests Triton.

Finding the tipping point

How much math is enough to keep the factory busy? The essay runs an experiment: multiply every number by 2, repeat times in a row, in one fused kernel. The data moves once no matter what, so raising repeat only adds math.

The amount of math you do for each byte you move is called compute intensity. Raise it and you slide from memory-bound to compute-bound.

The surprise: until you do about 50 operations per number, adding more math costs no extra time. The factory was sitting idle waiting for trucks anyway.

    
For a whole model, a good check is achieved FLOPS as a share of peak. If you're getting 80% of peak, you're at least 80% compute-bound, which is very good.

Overhead: the office paperwork

  

    
Overhead is everything that is neither math nor moving tensors: the Python interpreter running your code, PyTorch working out which kernel to call (called dispatch), and launching that kernel on the GPU.

    
The problem is that GPUs are absurdly fast and Python is not.

  

  

    
32 millionadditions per second in plain Python

    
280 thousandtiny PyTorch operations per second

    
9.75 millionFLOPs an A100 could do in the time Python does one

  

  

    
PyTorch is still usable because it runs asynchronously. The CPU hands the GPU a job and moves on to prepare the next one without waiting. If each GPU job is big, the CPU runs ahead, a queue builds up, and the overhead is hidden. If each job is tiny, the GPU finishes instantly and sits waiting for the office.

How to tell you're overhead-bound

    
Overhead doesn't grow when your data grows, but compute and memory do. So double your batch size. If the runtime grows only about 10% instead of doubling, you're overhead-bound. The "double the work" number above is this test.

    
You can also use a profiler: gaps on the GPU row mean the GPU is waiting on the CPU. The GPU-Util number in nvidia-smi measures roughly the same thing.

    
Fixes

    
Overhead is the price of flexibility: PyTorch is ready for something different at every step. If you don't need that, record the steps once and replay them. That's called tracing, as in jit.trace, FX or jax.jit. One level lower, CUDA Graphs record a whole sequence of kernel launches and replay them in one go; try the checkbox. The essay ends hopeful about a real JIT compiler called TorchDynamo, which later became the engine behind torch.compile.
